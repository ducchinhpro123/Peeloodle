# Remove in-memory pending-media retention; insertion stays local-first

Accepted and implemented. Presentation image insertion has been persist-first since the P18/P19 atomic-write hardening: `usePresentationSave.persistInsert` writes the planned document and the new bytes in one repository transaction and only then adopts the revision. The store's in-memory `pendingMedia` list, its `mediaForSave`/`clearPendingMedia` commands, `reconcileHeldMedia` and the `mediaRetentionBytes` budget were only reachable through the local-first insert command the editor had stopped calling, so they were removed along with the test-only `insertImage`/`replaceImage` store commands. Planning (`planImageInsert`, `planImageReplacement`, the refusal checks, `coverCrop`) stays pure and testable without storage; `adoptPersistedInsert`/`adoptPersistedReplacement` are the only image-write commands.

This is not a retreat from local-first. Persistence is IndexedDB by default, works offline, and needs no cloud connection; "local-first" describes where the bytes are stored, not when. Asset bytes stay in the repository for as long as any document or undo/redo snapshot can reference them, so redo reuses stored bytes, and a write omits media only when `repository.hasMedia` confirms the bytes are already stored. A failed insert leaves the document, the assets and the history untouched.

Consequences: document saves carry no media; the store holds document state only; `editor/history.ts` owns the bounded undo history (one completed gesture is one entry); conflict recovery re-keys copy media from the repository from content hashes. See ADR 0004 and [architecture](../slides-architecture.md).
